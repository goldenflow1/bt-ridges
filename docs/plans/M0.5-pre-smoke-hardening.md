## Goal

Make the measurements trustworthy without delaying the first integration check behind a full benchmark audit:

- Cost and cache figures distinguish reported values, estimates, and missing information.
- Checkers reject the known plausible wrong fixes.
- Results identify the task, runtime, and agent versions used, and comparisons enforce compatibility.
- Failure reports distinguish observed outcomes from inferred causes.
- Task weighting and keep/revert rules fit the current practice set.

M0.5A, M0.5B1, and M0.5B2 spend no inference money. Smoke, reconnaissance, evaluation, and confirmation trials are separate live work sharing the spending ceiling below. Full task validation uses Docker but no model calls.

### W1 — Cost provenance and accounting completeness (F1; M0.5A)

**Estimated effort:** 1–2 hours. **Dependencies:** requirement registration through W8; W2 consumes its records.

- Record cost_source as provider, estimate, or unknown, with an optional cost per attempt. A provider-reported zero is valid; an absent value is not automatically zero.
- For successful responses, use valid reported cost when present. If cost is absent but sufficient usage is reported, calculate an estimate and label it. Missing usage or an ambiguous transport failure remains unknown unless reconciled with provider records.
- Maintain separate accounting for reporting and spending enforcement. Reserve each attempt's pre-call estimate before dispatch. On an ambiguous timeout or lost response, retain that estimate as budget consumed/reserved even though reported expenditure remains unknown. A retry needs its own reservation and must fit the remaining budget.
- **Agent side (inside one task run):** calls are synchronous, so a timed-out response is discarded and never arrives late. `Wallet.charge()` replaces the attempt's reservation with its reported cost, or with its labelled usage-based estimate; a timeout or lost response keeps the reservation as consumed-but-unknown. A reservation is released only on evidence of no charge (e.g. a connection refused before sending). No attempt-ID idempotency is needed here. In production the platform proxy enforces the per-task cap independently; the agent's ledger drives its own stop decisions.
- **Host side (bench runner, across runs):** the authoritative reconciled figure is the key's cumulative `usage` from OpenRouter `GET /api/v1/key` (free, already used to validate the key), read before and after each run; the delta is the billed cost of that run. Per-call telemetry remains the diagnostic breakdown. The session ledger is keyed by run/trial ID, so re-reading a run's records never double-counts. If the key endpoint is unavailable, the run's cost falls back to telemetry and is labelled accordingly.
- An estimate is a conservative local control, not a guaranteed upper bound on provider billing; record and account for actual overruns when discovered.
- Summaries include provider-reported subtotal, estimated subtotal, estimated-call count, unknown-cost attempt count, cost_estimated, and accounting_complete. If any cost is unknown, show the accounted subtotal and leave the complete total unknown.
- Missing run telemetry stays unknown in the bench runner; never print an absent cost as $0.0000 or silently exclude it from a cost comparison.
- “Provider” means reported by the inference endpoint; “reconciled” means confirmed by the key-usage delta. Both are recorded.
- **Requirement:** H-WALLET-06: cost provenance and completeness survive from call records to run results; unknown attempts retain a budget reservation without being reported as confirmed expenditure.
- **Tests:** reported positive/zero cost; usage without cost; absent usage; timeout retains reservation; retry refused when its estimate no longer fits; reservation replaced (not doubled) by the reported cost; confirmed no-charge release; mixed attempts; missing run telemetry; host ledger computes run cost from key-usage deltas and never double-counts a re-read run.

### W5 — Outcomes, aggregation, and baseline promotion (F3/F5; minimal B1, full B2)

**Estimated effort:** 1–2 hours for B1 observations/labels and trial validity; 2–4 hours for B2 aggregation/promotion. **Dependencies:** W1/W2 accounting, W3 identity; W6 defines confirmation trials.

- **B1 minimum:** observations, final candidate identity, trial-validity decisions, manual annotations, and raw records. Simple per-set reconnaissance summaries are enough; --summarize and --promote-baseline do not block reconnaissance.
- **B2 completion:** compatible multi-run aggregation, the predefined confirmation protocol, immutable promotion, and comparison enforcement. Use actual reconnaissance logs to improve classification fixtures without relabelling uncertain causes as facts.

**Record observations before assigning a diagnosis.**

- Store execution outcome, termination reason, final patch hash, applicability result, final candidate guard/check status, verifier completion/reward, and accounting coverage separately.
- Emit final candidate telemetry after handoff selection, including alternate-candidate fallback. Earlier rejected candidates and loop messages must not determine the returned patch's label.
- Keep auto_label, empty manual_label, and manual_reason. Manual diagnoses such as wrong location, semantics, or performance are annotations; they do not override reward or mechanical failures.
- Define automatic precedence: contradictory authoritative outcomes → unknown; approved external setup failure → infrastructure-void; confirmed agent startup/execution/applicability failure → mechanical; completed reward 1 → solved; no usable candidate due to confirmed budget/deadline → that termination label; completed reward 0 with final guard/check failures → guard-failed/checks-failed; otherwise completed reward 0 → unsolved; insufficient evidence → unknown. Keep all underlying observations when several conditions coexist.
- A voluntary no-patch result after budget exhaustion is distinct from failed patch transport. A heuristic guard failure is not a confirmed verifier scope failure, and eligible + reward 0 is not proof of wrong semantics.

**Define valid and void trials by responsibility, not timing alone.**

- Record trial_validity as valid, void-infrastructure, or unresolved, with stage, evidence, and reason. A transient image pull, Docker/Compose startup, or health-check failure before agent execution can be void when logs establish that agent code was not responsible.
- An agent import, entrypoint, dependency, or startup defect counts as mechanical even if agent_main() was never called. A broken task image/configuration needs correction and revalidation; it is not a transient failure to retry indefinitely. Post-start failures are not automatically void, and unclear attribution stays unresolved until reviewed.
- Preserve every void attempt and link its replacement to the same planned trial slot. Void attempts are excluded from the agent solve-rate denominator, but included in infrastructure failure counts, wall time, and all spending records. They must be replaced before promotion; valid failed trials cannot be voided to improve results.
- Allow at most two setup replacements per planned slot. If they fail, stop that slot/cohort as infrastructure-blocked and fix the environment before scheduling a new documented run. Retries do not reset the session spending ceiling.

**Define aggregation inputs and weighting.**

- Preserve existing per-set execution. Add --summarize RUN_DIR [RUN_DIR ...] for explicit aggregation of compatible result directories, grouped by set, agent/configuration, and task-version cohort. Never blend public/dev/heldout into one headline score.
- Deduplicate trial IDs; retain failed, interrupted, void, and unknown trials. Conflicting duplicate records are errors. Separate physical attempts from planned valid-trial slots so replacements cannot inflate sample counts. Do not silently drop missing tasks or missing cost values.
- Compute solve fraction per task, then average equally over the frozen expected task set. Apply equivalent task weighting to comparable cost summaries and show coverage. If expected trials are missing, mark the result incomplete and do not present a completed-set mean. Report per-task attempt counts and solved-in-every-repeat separately.
- Distinguish initial evaluation, protocol-defined confirmation, setup replacement, and ad hoc diagnostic runs. W6's confirmation block is part of the experiment protocol declared before initial evaluation. Report its results separately and cumulatively with the original trials; it never replaces them. Other diagnostics cannot substitute for evaluation failures or change an immutable promoted baseline.

**Make baseline promotion explicit.**

- --baseline BASELINE_MANIFEST remains a comparison input. It does not save or promote a baseline.
- Add --promote-baseline OUT to the summary workflow. It writes an immutable manifest referencing selected run directories/trial IDs and their digests; it must not overwrite a kept baseline silently.
- Promotion requires at least three completed, distinct valid planned evaluation trials for **every** expected task, a fixed agent/configuration within the cohort, matching task/runtime identities, no missing expected slots, no unresolved validity/execution outcomes, and zero agent-attributable mechanical failures in the selected evaluation/confirmation cohort. Completed reward-zero failures are valid observations. Logged void setup attempts do not block promotion once their replacement slots complete.
- When a candidate experiment triggered W6 confirmation, promotion also references those trial IDs, initial and confirmation counts, and the decision. No initial failures disappear, and confirmation cannot hide a mechanical failure.
- Enforce those conditions per task, not by trusting a global --repeats value. Below three completed repeats, label the cohort reconnaissance; other failed conditions make it incomplete or incompatible, not promotable. Three successful repeats are evidence, not a guarantee of future stability.
- Comparisons reject task membership/version mismatches and incompatible runtime settings. Permit only declared experimental differences, such as a new bundle or model route. A changed checker requires rerunning the baseline on the new task version.
- Incomplete or estimated accounting may accompany a clearly qualified solve-rate baseline, but cannot support a claim about a reduction in billed cost. Cost-saving decisions require complete, comparable provider-reported or reconciled accounting on both sides.
- **Requirements:** B-RUN-02 covers observations, labels, and per-set/equal-task aggregation; B-RUN-03 covers promotion and comparison integrity.
- **Tests:** overlapping failures; stale candidate logs versus final fallback; missing telemetry/reward; weighting and duplicate trials; setup void with linked replacement; broken agent import remains mechanical; retry limit and unresolved attribution block promotion; missing expected slot; changed checker/runtime; incompatible agents within a cohort; allowed candidate bundle change; confirmation preserves original results; failed promotion writes no kept baseline.

### W6 — Keep/revert and confirmation protocol (F6; B2)

**Estimated effort:** 0.5–1 hour for policy/docs; protocol tests included in W5. **Dependencies:** W5 trial records and comparison support.

Update CLAUDE.md, docs/process/engineering-loop.md, and architecture.md §12.3/§17.2/§18.4 consistently:

| Change type | Evidence | Keep if |
|---|---|---|
| Reliability / mechanical | Focused regression proving the defect and fix; G0–G5; subsequent compatible bench check | The regression and gates pass, with no confirmed task regression under the protocol below. No solve-count gain is required. Offline fixes can proceed provisionally before the first live baseline. |
| Behaviour | Per-task before/after on the same frozen set, three initial repeats each, plus triggered paired confirmation | At least one additional task is solved 3/3, **or** comparable cost decreases by at least 15% with retained task coverage under the protocol; **both branches require no confirmed regression and no new agent mechanical failure**. |
| Any | Experiment record with comparison inputs and unresolved uncertainty | Provisional while the dev set has fewer than 15 tasks; re-evaluate on the expanded frozen set. This threshold is an engineering checkpoint, not statistical proof. |

**Predeclare this confirmation protocol before initial evaluation:**

1. Run three valid trials per task for baseline and candidate on matching task/runtime versions. Reuse a compatible baseline cohort only when its provenance and comparison settings match. Define the confirmation budget before starting.
2. A baseline 3/3 task falling to candidate 0/3 or 1/3 is a material regression and blocks keeping that candidate in this experiment. An agent-attributable mechanical failure also blocks it; confirmation does not erase that failure.
3. Any other observed per-task drop, including 3/3 → 2/3 or 2/3 → 1/3, triggers **one** additional block of three valid trials on **both versions**, limited to the affected tasks. Schedule baseline/candidate runs under matching conditions, alternating their order. This is planned confirmation, not an ad hoc rerun until success.
4. A drop persists when candidate solves fewer of these three confirmation trials than baseline; classify it as a confirmed regression and do not keep the candidate. If candidate matches or exceeds baseline in the confirmation block, classify the initial drop as not reproduced. Retain both blocks and report cumulative fractions; do not relabel a 5/6 result as 3/3 or claim statistical certainty. Equal but poor confirmation results identify an unstable task and must remain visible.
5. Perform at most one confirmation block per affected task. Missing valid trials, unresolved infrastructure attribution, or insufficient remaining budget leave the decision pending. Further work requires a new recorded experiment, not selective replacement of old results.

For the cost-saving branch, compare the identities of previously covered tasks: each must retain 3/3 initial performance or have its smaller drop classified as not reproduced by this protocol. A lost task cannot be exchanged for a different win. Require at least one solved task and complete comparable cost accounting; an all-zero solution is not a cost optimization success. Report mean per-task solve fractions, all raw repeat counts, and latency as well as the keep/revert decision, so changes outside consistently solved tasks remain visible.

Confirmation is an engineering decision rule for small samples, not a significance test. The same rule applies to both score-gain and cost-saving changes. Cost claims use W5's accounting criteria and matched resource limits.

Set a numerical held-out acceptance target before viewing results, and evaluate the final upload candidate three times. Dev results guide development but do not establish generalization. Held-out cases inspected and used for tuning become development cases and need fresh replacements.

### Budget note (live steps only)

**Set and verify a $30 total local-inference spending ceiling before step 2** (decided 2026-09-29; the key's own limit is $100). This is one shared envelope for smoke, reconnaissance, evaluation, setup replacements that incurred inference, confirmation, and diagnostics—not $30 per phase or process.
