## Implementation blockers

| Priority | Finding | Evidence / required correction |
|---|---|---|
| P1 | Correctly reconciled fault-run costs are rejected by the ordinary summary path. | `reconcile_proxy()` emits `matched-proxy`; `trusted_cost()` rejects that label, and its normal reconciliation would compare real cost against multiplied agent cost. A probe with real $0.002 and simulated $0.03 returned `None`. Add a validated proxy branch through aggregation and cost comparison; do not merely whitelist the label without validating its evidence. |
| P1 | Missing logs can look like complete zero-cost accounting. | `proxy_summary()` on a nonexistent file returns zero cost and `proxy_real_cost_complete=True`; with zero observed key delta it reconciles successfully. Require an explicit completed trial/request lifecycle and distinguish missing evidence from a known zero-request trial. |
| P1 | Some forwarded charges can disappear from the accounting record. | Only HTTP-200 costs contribute to `proxy_real_cost`. A synthetic HTTP-503 record with a known $0.003 charge was summarized as $0, complete. `forward()` exceptions bypass logging, and daemon handler threads can still be forwarding when `FaultProxy.__exit__()` returns. Log attempt start and completion/error, account for every known charge, retain uncertain requests, and stop scheduling until outstanding requests are resolved or conservatively reserved. |
| P1 | Fault identity is not preserved through promotion/comparison. | `cohort_key()` separates fault and clean runs during aggregation, but `promote()` drops the scenario from the stored cohort; comparison and confirmation checks omit it. A probe comparing a fault baseline with a clean candidate returned no compatibility problems. Persist scenario digest/configuration and enforce them at every comparison/confirmation boundary. |
| P1 | The ledger and proxy can use different API keys. | `run_bench.read_key()` prefers environment variables; `FaultProxy`, when not given a key, independently reads `~/.ridges/.env.miner`. The runner does not pass its selected key to the proxy. Pass one resolved key to both paths and test differing environment/file values using dummy keys. |
| P2 | Invalid multiplier configurations and missing response costs do not fail clearly. | `load_scenario()` accepts infinity and Boolean factors. When `usage.cost` is absent, multiplication silently leaves the response unscaled. Validate finite positive numeric factors, record scaling coverage, and mark the stress condition incomplete when cost cannot be scaled. |
| P2 | The claimed primary outcome is not yet a complete measurement contract. | The observer records patch hashes and termination, but missing patch artifacts can mean empty output, an exception, a run that never started, or missing evidence. Persist distinct categories. Finalization events currently live in logs; define and test their extraction and counts before the cohort starts. |

The session ledger also checks headroom before launch and records spend afterward; it does not persist an in-flight allowance before dispatch. A process crash or delayed key usage can therefore leave a reservation gap. Close that gap before treating the stated headroom as a robust experiment-wide spending control. Do not use multiplied agent telemetry as real spending when key usage is unavailable.

## What ×15 does and does not test

The ratio $0.147 / $0.0097 is roughly 15.2, but it compares different tasks, routing, token counts, and conditions. It is not an identified per-call price multiplier. The production mean also refers to the 25 cost-reported screening runs, not all 30 scheduled slots.

The current proxy changes **returned** `usage.cost`. It leaves the agent's pre-call price estimates, affordability checks, and reservations at the original prices. A request may fit its estimate, then consume 15 times its actual price after completion, potentially overrunning a phase or the finishing allowance. That is useful for testing unexpected billing pressure; it is not a faithful expensive-model or provider-hard-cap simulation. Capture these overruns explicitly and label the condition accordingly.

Real provider pricing is unchanged for a given forwarded request. Total experiment spending is not guaranteed unchanged: the altered feedback can change how many requests each version makes. Missing `usage.cost` can also make some attempts escape the intended multiplier.

## Correct the declared decision rule

The proposed rule is not the existing [engineering-loop §5a](../process/engineering-loop.md):

1. Fewer empty patches is a useful mechanism metric, but it is not the behavioral acceptance criterion currently specified.
2. The existing gain is an additional task solved on all three trials, or attributable cost at most 85% of baseline while preserving coverage. Both branches also require no confirmed regression and no new mechanical failure.
3. A solve gain must not override a regression elsewhere. The proposal's final “or” needs this qualification.
4. Drops such as 3/3 → 2/3 or 2/3 → 1/3 require the one paired confirmation block; they cannot be accepted merely because they are not the immediate 3/3 → 1/3 rejection case.
5. Missing evidence or insufficient pressure is **inconclusive/pending**, not proof that B2/B3 is ineffective. A demonstrated regression and a complete no-gain result should remain distinguishable from an invalid or uninformative experiment.

Use no-patch rate as the primary diagnostic metric and retain §5a for release acceptance. If a no-patch-based acceptance criterion is desired instead, explicitly revise the process prospectively; do not call it the existing rule. Empty output is not synonymous with production error 1000, which can also cover exceptions.

## Recommended sequence

1. Fix the blockers above and add negative tests for missing logs, in-flight requests, billed error responses, mismatched scenarios, wrong-key selection, invalid factors, and the complete summary/comparison path.
2. Save a small technical-pilot protocol before paid work: for example, four preselected development tasks, one A/B pair each. Test proxy reachability from the task container, cost reconciliation, multiplier coverage, stress exposure, event extraction, and explicit empty-output classification. Exclude pilot results from the final confirmatory cohort.
3. Use the pilot to determine whether ×15 reaches the intended budget-pressure path without simply exhausting both arms before any useful work. If the stress configuration changes, freeze a new scenario identity and protocol before the main cohort.
4. Freeze both bundles, task/runtime/configuration identities, full scenario content/hash, and the 102-slot schedule. Counterbalance A/B versus B/A order across pairs; run full tasks serially. Ensure the aggregator can combine the resulting per-task runs into the declared cohort without discarding provenance.
5. Declare a real-dollar pilot limit, main-cohort scheduling limit, stop conditions, and headroom for confirmations and later normal/G7 evaluation. The $1.0–1.2 and 4.5-hour figures are estimates, not enforced limits. At the existing $0.29 allowance, 102 reservations sum to $29.58 before confirmations; the reported $20.72 headroom cannot guarantee that worst-case schedule. Serial reconciliation can release headroom as actual costs become known.
6. Run the main stress comparison only after the pilot and evidence pipeline pass. Report per-task paired outcomes, distinct failure categories, real and simulated costs, budget overshoots, and B2/B3 activation rates. Then apply the declared decision rule and normal-condition comparison before frozen-release G7.

The reported $20.72 key headroom and $9.28 ledger usage were supplied in the proposal; this review did not independently refresh the live account balance.
